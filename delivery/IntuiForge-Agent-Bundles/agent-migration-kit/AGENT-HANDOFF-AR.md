# تسليم تنفيذي صارم — تثبيت IntuiForge وربطه وترحيل RichViz

## أ. التعريف
- المشروع: IntuiForge — Intelligent UI Engine.
- المهمة: تثبيت الحزمة المحلية، دمجها فعليًا في المشروع المستهدف، إعداد مسار موثوق لتحديثها من مستودع GitHub الخاص، ثم إزالة نسخة RichViz القديمة من المشروع المستهدف بعد نجاح التحقق فقط.
- النمط: STRICT؛ نفّذ بالتسلسل وبوكيل واحد. لا تستخدم وكلاء فرعيين.
- مستودع المصدر الرسمي: https://github.com/Abdulrahman3M/IntuiForge (خاص، فرع `main`).
- ملف الحزمة: `intuiforge-engine-1.0.0.tgz`؛ الإصدار `1.0.0`؛ SHA-256 `a174191e76f1b7838aa6a9f8a8ed14308f0f3ae906ab8a80b1a983fa69170a46`.

## ب. الهدف
ثبّت IntuiForge في الموضع الصحيح حسب بنية المشروع ومدير حزمه، اربطه فعليًا بواجهة/مسار المحتوى المطلوب، اختبره داخل سياق المشروع، وثبّت رابط مستودع GitHub الخاص وتعليمات تحديث قابلة للتكرار. احذف تثبيت RichViz القديم من المشروع المستهدف فقط بعد اجتياز جميع بوابات القبول أدناه.

## ج. الحالة والقيود المعروفة
- الحزمة محلية خاصة وغير منشورة على npm؛ لا تحاول تثبيتها بالاسم من سجل عام.
- الحزمة تعمل عبر exports مثل `@intuiforge/engine`, `/article`, `/article-renderer`, `/host`, `/design-system`, `/state`, `/richviz`.
- IntuiForge يحتوي عمدًا طبقة توافق RichViz. لا تحذفها ولا تعدّل ملفات vendor أو الأصول أو إشعارات تراخيص الطرف الثالث ضمن هذه المهمة.
- مستودع GitHub خاص. تحقق من صلاحية القراءة قبل تصميم تحديث آلي. لا تضع رموز وصول أو أسرارًا في الملفات أو السجل.
- المشروع المستهدف لم يُحدّد هنا؛ اكتشفه من مساحة العمل التي يعمل فيها الوكيل ولا تفترض مساره أو تقنياته.

## د. النتيجة المطلوبة
1. اعتماد الحزمة بعد مطابقة SHA-256 مع القيمة أعلاه.
2. تسجيل تبعية IntuiForge بالطريقة التي تدعم مدير حزم المشروع، وحفظ ملف القفل المحدّث.
3. تنفيذ تكامل فعلي يستعمل API عامة موثقة ويعرض وظيفة متوافقة مع المشروع. لا يكفي نسخ الملفات أو إضافة تبعية غير مستخدمة.
4. إضافة توثيق محلي لرابط GitHub وطريقة سحب تحديث ومراجعته وتثبيته والتحقق منه والرجوع عنه.
5. إبقاء RichViz القديم حتى ينجح تثبيت IntuiForge والتكامل والبناء والفحوصات ذات الصلة والفحص المرئي عند توفر بيئة معتمدة.
6. إزالة مجلد/تبعية التشغيل القديمة لـRichViz من المشروع المستهدف فقط بعد نجاح كل بوابات القبول. راجع diff وتأكد من عدم إزالة محتوى المستخدم أو ملفات البيانات أو التراخيص اللازمة. إذا كانت الإزالة ستكسر محتوى أو صفحات أو عقدًا عامًا، أوقف الإزالة ووثّق التعارض؛ لا تتجاوز بوابة الأمان.

## هـ. النطاق والحفظ
### داخل النطاق
- فحص تعليمات المشروع، تحديد موضع تثبيت الحزمة، تثبيت محلي وتكامل محدود، توثيق تحديث GitHub، حذف RichViz القديم عند تحقق الشروط.
### خارج النطاق
- نشر IntuiForge على npm أو جعل مستودعه عامًا.
- حذف RichViz من مستودع IntuiForge أو طبقة التوافق أو أرشيفات النسخ الاحتياطي.
- إعادة تصميم واسعة، ترحيل جماعي للمحتوى، تغيير هويات أو مسارات أو بيانات محفوظة.
- تضمين أسرار GitHub أو تغيير إعدادات صلاحيات الحساب.
### يجب الحفاظ عليه
- بيانات المشروع ومحتواه وروابطه وسلوكه غير المرتبط بالمحرك، توافق RTL/LTR وإمكانية الوصول، ملف القفل والتبعيات غير المتعلقة بالمهمة، وكل تراخيص الطرف الثالث والإشعارات المطلوبة.
- لا تعدّل شيفرة لا تتعلق بالمهمة لمجرد ملاحظة مشكلة أخرى.

## و. فحص إلزامي قبل التنفيذ
1. حدّد جذر المشروع المستهدف وتحقق من هوية المستودع والفرع وحالة الملفات. لا تستبدل تغييرات موجودة.
2. ابحث عن `AGENTS.md` و`CLAUDE.md` و`CODEX.md` وكل تعليمات الوكلاء العامة/المتداخلة؛ اقرأ جميع ما ينطبق على الملفات المستهدفة وحدد أولوية التعليمات قبل أي تعديل.
3. افحص manifest ومدير الحزم وملف القفل وأوامر التطوير والبناء والاختبارات وواجهات الصفحات/البيانات الحالية.
4. ابحث عن كل مراجع RichViz ومسارات الأصول والصفحات والأنماط والمحتوى الذي يعتمد عليه. صنّفها إلى تشغيل/تبعية/بيانات/تراخيص؛ لا تحذفها تخمينًا.
5. اقرأ أدلة API والتكامل وMIGRATION وQUICKSTART المرفقة بالحزمة أو الموجودة في مستودع المحرك. تحقق من API من ملفات التصدير الفعلية قبل استعمالها.
6. استدع مهارة `token-optimization` المستقلة للتنفيذ الكبير. استخدم قراءات نطاقية انتقائية ونقاط تحقق موجزة قابلة لإعادة الاستخدام، واستدعاءات محدودة غير مكررة. لا تقلّص الاختبارات أو متطلبات السلامة أو القبول لتوفير الرموز.
7. تحقق من GitHub عبر وسيلة مصرح بها (`gh auth status` و`git ls-remote` أو ما يعادلهما) دون طباعة رمز. لأن المستودع خاص، إذا لم تتوفر مصادقة صالحة، تابع من ZIP للتثبيت فقط، واجعل ربط التحديثات الآلية `UNVERIFIED`، ولا تدّع أن الاتصال تم.

## ز. مصدر الحقيقة والمعمارية
استخدم الحزمة المنشورة داخل هذا ZIP كنسخة تثبيت أولية ثابتة، ومستودع GitHub الخاص كمصدر النسخ المستقبلية. لا تربط تطبيق المستخدم مباشرة بفرع متغير دون قفل إصدار وبصمة. اختر وسيلة محلية متوافقة مع بنية المشروع (ملف أرشيف معتمد/دليل vendor أو آلية المشروع) وسجّل موضعها. لا تخترع نظام submodule أو CI جديدًا إن لم يكن مطلوبًا في المشروع.

## ح. متطلبات التنفيذ التفصيلية
1. تحقق من الأرشيف:
   - استخرج البصمة من الملف نفسه، وقارنها بالقيمة المتوقعة وبـ`release-manifest.json` و`SHA256SUMS.txt`.
   - عند عدم التطابق: أوقف التثبيت، واحتفظ بالملفات، وبلّغ عن `FAIL`.
2. ثبّت الحزمة بالطريقة الرسمية الملائمة للمشروع. افحص شجرة التبعيات وملف القفل وتأكد أن النسخة المحلولة هي 1.0.0 ومن الملف المحلي المتوقع.
3. نفّذ تكاملًا حقيقيًا صغيرًا ومتسقًا مع المشروع. استخدم مدخلات موثقة ومتحققًا منها؛ لا تغير تخزين أو هوية أو مسارات قائمة دون حاجة مثبتة.
4. أضف تعليمات تحديث محلية تتضمن رابط المستودع الخاص، الفرع، المتطلبات المصادقة، التحقق من manifest/SHA، مراجعة diff، تحديث التبعية والقفل، اختبارات التوافق، والرجوع إلى النسخة السابقة. لا تسجل رموز وصول.
5. قبل الإزالة، تحقق من كل بوابات القبول في القسم ل. إذا فشل شرط أو بقي غير متحقق، لا تحذف RichViz، وأكمل الأعمال المستقلة الآمنة وبلّغ `PARTIALLY COMPLETE` مع السبب.
6. بعد تحقق البوابات، احذف فقط تبعية/نسخة التشغيل القديمة المحددة في المشروع المستهدف، ونظّف المراجع التابعة اللازمة فقط. لا تحذف أرشيف المصدر أو ملفات البيانات أو إشعارات الترخيص المطلوبة قانونيًا. احتفظ بإمكانية الرجوع عبر Git/نسخة مرجعية آمنة.

## ط. الحالات الحدية والتعامل معها
- لا يوجد manifest أو ملف قفل: اتبع دليل مدير الحزم الرسمي للمشروع؛ لا تنشئ نظام بناء جديدًا.
- مشروع بلا npm: لا تفرض npm. اعرض التعارض الدقيق بين الحزمة وآلية المشروع، واطلب قرار المالك فقط إذا لم يوجد مسار تكامل مدعوم وآمن.
- API أو بنية المشروع غير متوافقة: أوقف جزء التكامل المتأثر بعد توثيق الدليل؛ لا تضف shim غير موثق.
- المستودع الخاص غير متاح: لا تضع بيانات اعتماد في المستودع ولا تدّع إعداد التحديث التلقائي. يمكن توثيق رابط التحديث ومسار يدوي، مع وضع الوصول المستقبلي `UNVERIFIED`.
- استخدام RichViz لا يزال قائمًا في صفحات أو بيانات لازمة: أبقِ التثبيت القديم؛ لا تحذف ملفات لازمة ولا تغيّر المحتوى بصمت.
- فشل بناء/اختبار/عرض أو اختلاف بصمة: أبقِ RichViz وأعد الحالة السابقة لتعديلات التكامل إن لزم، دون المساس بتغييرات المالك السابقة.
- لا تلمس الملفات غير المتتبعة أو التعديلات السابقة إلا إذا أثبت فحصك أنها تخص هذه المهمة.

## ي. التحقق
شغّل فقط الفحوص المرتبطة بالملفات والمسارات المتغيرة:
- تدقيق SHA-256 وبيانات الإصدار ووجود الحزمة المثبتة: إلزامي.
- فحص الأنواع/التحليل والبناء والاختبارات المركزة المناسبة للتكامل: إلزامي بحسب أدوات المشروع.
- تشغيل الصفحة/التدفق المتأثر وفحص التفاعل وConsole والأخطاء: عند توفر بيئة المتصفح المعتمدة.
- اختبر RTL وLTR والاستجابة وإمكانية الوصول/لوحة المفاتيح إذا تأثرت.
- تحقق بعد إزالة RichViz من عدم وجود مراجع تشغيل معلقة ضمن النطاق، ومن بقاء بيانات المستخدم والتراخيص اللازمة.
- لا تشغّل اختبارات المستودع كلها دون سبب رسمي موثق. لا تصلح إخفاقات غير مرتبطة.
- أبلغ كل فحص بـ`PASS` أو `FAIL` أو `UNVERIFIED`؛ لا تصف فحصًا لم يُنفذ بأنه ناجح.

## ك. بوابة حذف RichViz — يجب اجتيازها جميعًا
- [ ] ثبت أن `@intuiforge/engine` 1.0.0 موجود في مدير الحزم/القفل ومصدره الملف المتوقع، والبصمة صحيحة.
- [ ] تكامل IntuiForge فعلي ويعرض الوظيفة المتفق عليها في التطبيق المستهدف.
- [ ] البناء والفحوص المركزة المتعلقة بالتكامل كلها `PASS`.
- [ ] تحقق التشغيل في البيئة المناسبة؛ إذا تعذر المتصفح اذكره `UNVERIFIED` ولا تحذف RichViz.
- [ ] فُحصت مراجع RichViz، ولم يبق اعتماد تشغيل ضروري أو محتوى يتطلبه.
- [ ] تمت مراجعة التغيير المقترح للإزالة والتأكد من أنه لا يحذف بيانات مستخدم أو تراخيص مطلوبة أو أصلًا خارج النطاق.
- [ ] مسار التراجع متاح (Git نظيف/لقطة/نسخة موثقة) وملف القفل يعكس الحالة النهائية.

إذا لم تجتز جميع البنود، **لا تحذف RichViz**.

## ل. التسلسل التنفيذي
1. افحص تعليمات الوكلاء وحالة المستودع والموضع المستهدف.
2. افهم مدير الحزم، التكامل الحالي، RichViz ومستهلكيه.
3. تحقق من ZIP والبصمة والإصدار والتراخيص.
4. تحقق من مصادقة GitHub وصلاحية قراءة الرابط الخاص دون كشف أسرار.
5. ثبّت IntuiForge مع إبقاء RichViz.
6. نفّذ التكامل الأصغر الكامل ووثق طريقة التحديث والرجوع.
7. شغّل التحقق المركّز وسجّل أدلته.
8. قيّم بوابة الحذف حرفيًا. إن اجتازتها جميعًا، أزل نسخة RichViz التشغيلية القديمة من المشروع المستهدف فقط.
9. أعد البناء والفحوص اللازمة بعد الإزالة، وافحص diff والقفل والبيانات والتراخيص.
10. حدّث توثيق المشروع المتأثر فقط. اتبع قواعده الخاصة بالسجل؛ لا تخترع NID/CID/RID أو أرقام إصدار.
11. راجع التغييرات النهائية، وقدّم التقرير أدناه.

## م. معايير القبول
- [ ] بصمة الأرشيف مطابقة للـmanifest والقيمة المحددة.
- [ ] IntuiForge مثبت من الأرشيف الصحيح ومدرج في القفل.
- [ ] هناك تكامل عامل في موضع مناسب داخل التطبيق، وليس تبعية غير مستعملة.
- [ ] الفحوص ذات الصلة موثقة بـPASS/FAIL/UNVERIFIED وبأدلة حقيقية.
- [ ] دليل GitHub يذكر الرابط والخصوصية والمصادقة وطريقة تحديث إصدار مثبت ومراجعة SHA والرجوع.
- [ ] لا يوجد سر وصول في الملفات أو السجل.
- [ ] إزالة RichViz لا تتم إلا بعد نجاح جميع بوابات الحذف؛ وإذا تعذر التحقق فهو محفوظ.
- [ ] لم تُحذف بيانات أو تراخيص لازمة ولم تتغير أعمال غير متعلقة.
- [ ] روجعت قواعد السجل وأمثلة حديثة، واستخدم المولد الرسمي إن وجد؛ لا تُختلق المعرفات.
- [ ] لا تبقى عناصر TODO أو placeholders أو stubs ضمن نطاق المهمة دون تصريح موثق.

## ن. تعريف الاكتمال
`COMPLETE` فقط إذا ثبت التثبيت والتكامل والبناء والفحوص، وأُعد مسار تحديث GitHub موثق ومتاح للمصادقة، واجتازت بوابة إزالة RichViz وتمت الإزالة بأمان، واكتمل التوثيق المطلوب. إذا فشل الوصول الخاص إلى GitHub فاذكر ربط التحديثات غير متحقق ولا تدّع الاكتمال الكامل لهذا الجزء. إذا لم تجتز بوابة الإزالة، أبلغ `PARTIALLY COMPLETE` واترك RichViz سليمًا.

## س. التقرير النهائي المطلوب
- الحالة النهائية: `COMPLETE` أو `PARTIALLY COMPLETE` أو `BLOCKED`.
- ملخص التثبيت والتكامل وموضعه.
- طريقة مدير الحزم ونسخة/بصمة الأرشيف.
- حالة وصول GitHub الخاص وإعداد التحديثات، مع ذكر أي متطلب تسجيل دخول دون كشف بيانات اعتماد.
- نتيجة كل بوابة حذف، وما أزيل تحديدًا أو سبب إبقاء RichViz.
- قائمة الملفات المعدلة في المشروع المستهدف.
- الفحوص بأدلتها: `PASS` / `FAIL` / `UNVERIFIED`.
- التوثيق والسجل الذي جرى تحديثه، وأي عناصر متبقية ذات صلة.
- تأكيد عدم استيعاب تغييرات غير متعلقة وعدم كشف أسرار.
